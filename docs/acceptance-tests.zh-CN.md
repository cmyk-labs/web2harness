<a id="release-requirements"></a>

## 发布要求与用例目录

每次版本发布，包括预览版，都必须在当前候选版本上重新执行 CAP-001～CAP-005（按各用例适用条件），全部通过并留存证据后再推送会触发发布的 tag 或公开发布。失败、受阻或未执行均不能勾选通过；修复后重新验收，保留原失败记录。这些用例是人工发布门禁，目前不由 `bun run verify` 或 GitHub Actions 自动执行或强制检查。

| 编号 | 目标能力 | 执行频率 | 关键通过依据 |
| --- | --- | --- | --- |
| [CAP-001](#cap-001) | Code Mode、并行工具、原生补丁及结果回读 | 每次发布 | `exec` 内真实 `Promise.all` 读取，两份返回值、补丁事件和结果文件一致。 |
| [CAP-002](#cap-002) | 异步 cell 生命周期与等待续接 | 每次发布 | 一个 15 秒任务、运行中的 cell、对同一 cell 的 `wait` 和落盘结果。 |
| [CAP-003](#cap-003) | 真实子 agent 委派、并行执行、结果汇总和只读边界 | 每次发布 | 三个独立子 agent、实际工具执行、完成结果和项目文件前后核对。 |
| [CAP-004](#cap-004) | 明确模型家族、五档选择、三倍预算与发送记账 | 自动模式发布；具备两家族及 Pro 的 DEV 账户 | 两家族十档菜单校验、四入口真实读写、目录预算及模型回执。 |
| [CAP-005](#cap-005) | 本地计数、回执补记与参考分离 | 自动模式发布 | 真实发送/压缩、故障夹具、双语UI及迁移证据。 |

这些用例不替代[发布手册](release.zh-CN.md#authenticated-runtime)中的取消、压缩、会话复用、MCP、平台和安装升级检查。影响已验收行为的源码或加载运行时发生变化后，必须对新的候选版本重新取得相关证据。

<a id="preparation"></a>

## 执行准备

先遵守[标准隔离测试流程](development.zh-CN.md#standard-isolated-test-procedure)：从 `bun run dev:launcher` 启动并核实 DEV 归属，使用独立登录和当前候选源码，通过 `bun run dev:codex` 运行真实 Codex 任务。不得使用模拟器或夹具浏览器代替真实 Web 模型验收。

1. 记录候选版本、提交、未提交差异的标识、实际加载的运行时、Codex 版本、系统/架构、账户计划、Web 模型完整 ID、思考强度及交互/工具模式。先完成生产配置/认证哈希和进程身份基线。
2. 基线用例采用 **Native Tools + Automatic**，明确选择账户实际支持的 Web 模型和强度。子 agent 沿用该模型，不得为通过测试改用原生 API。其他模式、模型和平台按发布范围补测；单组通过不能外推到全部组合。
3. 将 `<TEST_DIR>` 替换为本次新建的独立 DEV 测试目录的绝对路径，允许任务在其中写文件。不要在用户工作目录覆盖现有同名文件。CAP-001 和 CAP-002 串行执行，CAP-002 沿用 CAP-001 的 Codex 会话和目录。
4. 为 CAP-003 准备与候选版本一致的独立 DEV 源码副本，以其绝对路径替换 `<PROJECT_DIR>`，以实际模型 ID 替换 `<WEB_MODEL_ID>`。在新会话中使用只读沙箱，父任务和子任务均不得写入源码、日志或构建产物。测试前记录文件清单、哈希及已有 Git 状态。
5. 只在 CAP-003 内并行运行三个子任务；不要同时启动其他认证验收。外层验收者在被测目录之外记录日志、文件快照和版本结果，不委派只读子任务写工作日志。验收后按隔离流程复核生产边界。

以下提示词可直接复制，先替换其中的路径和模型占位符。工具名称、参数和调用范围以当前 Codex 实际声明为准；顶层工具不一定出现在 exec 的 `tools` 导出中。

## CAP-001：Code Mode 并行读取与原生补丁

**提示词**

```text
仅在当前测试目录 <TEST_DIR> 操作。先创建 a.txt 和 b.txt，内容分别为 ALPHA 和 BETA。
然后必须通过 Code Mode 的 exec，用 Promise.all 并行调用两个读取文件的工具，将两个结果返回。
再通过 exec 调用 apply_patch 创建 result.txt，内容为 ALPHA-BETA，最后读取验证。
如果没有 exec，请明确报告，不要改用其他方式完成。不要修改测试目录之外的文件。
```

**通过条件与证据**

- 日志中存在真实 Codex `exec` 调用，原始脚本使用 `Promise.all` 发出两个独立读取工具调用；不是一条命令顺序读取，也不是直接返回预期常量。
- 两个实际工具结果分别读到 ALPHA 和 BETA。保存调用 ID、原始工具身份及返回结果，确认两项读取都已完成。
- 后续 `exec` 确实调用 `apply_patch` 创建 `result.txt`，保存补丁事件；仅用 shell 写入或手工补文件不算通过。
- 最后执行真实文件读取或内容断言。文件正文必须为 `ALPHA-BETA`，允许正常末尾换行；核对 a.txt、b.txt 和 result.txt 的实际内容及修改范围。

缺少 exec、未实际并行、工具报错后未完成要求、输出不符或越界写入均不得记为通过。

<a id="cap-002"></a>

## CAP-002：Code Mode 等待与同任务续接

**提示词**

```text
测试 Code Mode 等待续接。仅在当前测试目录 <TEST_DIR> 操作：
在 exec 中执行一个等待 15 秒后返回 WAIT-110-OK 的任务，按照当前 exec 声明设置较短的 yield_time_ms，
让 exec 先返回运行中的 cell_id。然后调用 wait，直到取得结果。
不得重新启动同一个任务，不得在外部另开任务代替等待。
最后将取得的标记通过 apply_patch 写入 wait-result.txt，再读取验证。
如果 exec 或 wait 不可用，请明确报告，不要绕过。
```

**通过条件与证据**

- 原始脚本只启动一次 15 秒任务，yield 小于任务等待时间，例如 1000ms；真实 exec 返回“运行中”及 cell ID，而非直接完成。
- 后续使用 Code Mode 的 `wait` 续接该 cell。允许多次 wait，但 cell ID 必须一致；记录各次调用与最终输出，不得重新提交计时脚本。
- 从完成的任务取得 `WAIT-110-OK`，经真实 `apply_patch` 写入 `wait-result.txt`，回读内容一致，允许正常末尾换行。
- 保存原始脚本、调用时间、运行中返回、cell ID、wait 返回、补丁事件及文件验证；不能用整轮对话耗时推断脚本等待了 15 秒。

如果当前 exec 声明支持 `setTimeout`，可用它实现计时；不得凭顶层 `clock.sleep` 的存在猜测 `tools.clock__sleep` 也可调用。`WAIT-110-OK` 是固定验收标记，不代表被测版本必须为 1.1.0。没有经历运行中 cell 和同 cell 续接的尝试不得记为通过。

<a id="cap-003"></a>

## CAP-003：三个真实子 agent 并行只读分析

**提示词**

```text
请实际委派 3 个 Codex 子 agent 并行工作，不要由你扮演三个角色。
项目路径：<PROJECT_DIR>。三个子 agent 均继续使用当前 Web 模型 <WEB_MODEL_ID>，不切换到原生 API。
使用当前 Codex 实际声明或发现的委派工具，不猜测工具名。

子 agent 1：只读调研 GitHub，找一个与当前项目接近的开源项目，实际访问仓库、核对开源许可证，
给出仓库链接、相似点及依据。访问失败要如实报告，不把记忆或搜索摘要当成已访问仓库。
子 agent 2：只读分析当前项目实现了哪些功能，给出源码路径和依据，区分静态实现与运行验证。
子 agent 3：只读分析当前项目有哪些优化点或可新增功能，给出源码依据，区分已有实现与建议，
不得把静态推断表述为已复现故障。

最后由你等待并汇总三者的结果，列出实际子 agent ID 和对应结论，并结束已完成的子任务。
全程只分析，不允许修改或新增任何项目文件，不写工作日志，不运行会产生文件的构建或测试，
不提交或发布，不再创建额外子 agent。若无法完成实际委派、并行执行或 GitHub 访问，明确报告失败环节，
不得模拟成功。保持只读沙箱和正常权限边界。
```

**通过条件与证据**

- 存在三个不同的真实子 agent ID、父子关系及委派事件。三次委派在同一并行批次发出，执行生命周期有重叠；三次串行任务或三段角色文本不算并行委派。
- 核对每个子任务实际使用的 Web 模型及只读沙箱，以运行时记录或等效证据确认；仅凭“继承模型”的提示词不能证明没有切换模型。
- 子 agent 1 有成功的 GitHub 仓库访问与许可证证据；另外两个有真实源码读取记录，结论与实际职责对应。局部页面访问失败必须记录，不能拿失败页面支撑结论。
- 三个子任务都完成，父任务实际取得三份结果并输出汇总。仅成功创建子任务、CLI 退出码为零或子任务自称成功均不够。
- 测试前后项目文件清单、内容哈希、已有修改及未跟踪文件保持一致，并核对文件变更事件；已有修改不得清理。任何项目写入均不通过。

只读检查覆盖父任务和三个子任务。测试报告在外层证据目录保存，不允许为了记录验收而让这些任务写入被测项目。

## CAP-004：模型家族、思考档位与通用预算

适用范围：每次包含自动模式的发布。使用独立登录、可选择 GPT-5.6 Sol 与 GPT-6 且五档均可用的 DEV 账户；缺少账户能力应记为未执行。采用本页准备步骤和任务独占工作区。

1. 从默认模型开始，交替选择两个家族及 Instant、Medium、High、Extra High、Pro；通过共享适配器核对实际选中家族及滑块位置。保留菜单证据，覆盖标题独立显示模型版本的布局。不得通过手动预选绕过适配器选择。
2. 对四个入口 GPT-5.6 Sol、GPT-5.6 Sol Pro、GPT-6、GPT-6 Pro 分别启动真实 DEV Codex 任务。普通入口选一个非 Pro 档，Pro 固定 max。给定输入文件，提示：“读取 input.txt，通过原生补丁写入 result.txt，再运行命令验证内容与输入一致，最后报告结果。”留存实际工具调用、回读和产物哈希；确认浏览器及用量回执的模型一致。
3. 核对 Pro 目录中普通入口提供四档、两个 Pro 入口固定 max；分别以标准及三倍配置检查四入口窗口和压缩阈值恰好相差三倍，档位分组不变。单次消息限制保持不变。预算目录检查不代表已测得服务端容量。
4. 用隔离 DOM 夹具覆盖 6/GPT-6 两种名称、隐藏或 inert 菜单、错误家族和冲突提示。无法验证时必须阻止发送；夹具不能代替步骤 1、2 的认证实测。

缺少模型切换、工具执行或文件证据，或将 5.6 误当成 6，均不通过。普通 GPT-6 消息需独立计数，不进入 Pro 额度计数。 中文 Pro 页面仍显示“停止”时，延迟出现助手节点不能被视为生成停止；整体任务仍受原有截止时间约束。结束后关闭本例拥有的 DEV 页面／任务并核对生产边界，保留证据。

视口或回复提取变更还需运行隔离 Electron 选模夹具，覆盖100%与125%缩放：切换标签、其他任务结束及隐藏/显示窗口后，模型菜单与页面尺寸应保持稳定。原生窗口尺寸暂时为0×0时，应保留有效的界面测量，不能把网页裁剪为1×1。执行文件预览移动、重复段落、空段落后续填充、KaTeX源码保留的DOM回归，真实文本或链接修改仍须报错。使用重建后的共享运行时完成认证DEV的读取 → 补丁 → 命令任务。新配置和缺少聊天记录偏好时默认选择临时聊天，已有明确历史偏好重载后仍保留。夹具结果不能代替认证验收。

<a id="cap-005"></a>

## CAP-005：本地发送统计与回执补记

适用于包含自动模式的发布。使用独立认证的DEV配置、专属工作区及候选共享运行时。

1. 记录初始账号计数。选择可用的非Pro模型执行CAP-004读文件/补丁/命令任务；核对网页接受提交次数、账本增量、选定模型/档位，以及任务/工具结果续发用途。没有网页发送的工具调用不增加次数。
2. 执行真实隔离压缩，仅在提交网页消息时产生压缩用途回执。三倍预算不能直接乘以次数。
3. 在专属传输夹具中模拟落盘后丢失确认、落盘前上报中断；重启回执消费者，每个已接受ID只记一次。没有接受证据的发送开始项单列。损坏项保留并提示错误。故障夹具不能替代第1–2步认证实测。
4. 渲染双语及窄窗口：按模型合并思考档位和发送用途；Pro 合计包含两个家族及型号未识别的 Pro，不包含普通 Sol，并与回执证据一致。不另列档位明细。切换参考套餐/时期不改变账号统计或网页选定模型。未知上限统一显示“-”，保留选中的参考时期，简短说明位于各自表后；来源及核验状态保存在政策元数据中。

保留回执、工具与文件证据，旧账本迁移结果、生命周期状态及生产边界对比。缺失投递证据、重复计数、重放网页发送，或由本地滚动次数计算官方余额均失败。

## 版本结果记录

每个候选版本单独建立结果记录，原始日志、rollout、文件快照及产物保存在忽略的 `output/` 或私有 DEV 存储；对外仅提供脱敏结论。发布证据的完整字段与保密要求见[发布手册](release.zh-CN.md#validation-evidence)。

记录版本/提交及候选差异标识、测试日期与执行者、实际运行时、Codex 版本、系统/架构、模型/强度、模式、会话 ID，以及每项的尝试编号、证据位置、实际结果、失败原因和后续处理。每次重新验收保留前次记录。

| 用例 | 尝试 | 状态 | 调用/产物/哈希证据 | 实际结果与问题 |

| CAP-002 | 待执行 | 未执行 | 待记录 | 待记录 |
| CAP-003 | 待执行 | 未执行 | 待记录 | 待记录 |

状态使用“通过 / 失败 / 未执行”，受阻时写明原因并保持未通过。排障应区分模型返回、桥接转换、Codex 执行器、权限/账户/网络环境，不在缺少证据时统一归因于某一层。

<a id="extend-cases"></a>

## 新增与维护用例

新增目标能力或改变已有能力时，同步增加或更新对应的真实验收用例，并在发布前执行。用例编号从 `CAP-006` 继续递增，不因版本变化重编号或复用旧编号。维护中英文相同编号、提示词语义和通过条件，并更新上方目录。

新用例默认纳入每次发布基线；如果仅适用于特定模式、平台或账户，明确适用条件和所需测试环境，仍需在每次相关发布中执行。不能为了绕过失败临时缩小范围、降低通过标准或把未执行改为不适用。退役用例保留编号、原因和替代用例引用。

新增用例采用以下格式：

```text
编号与名称：CAP-006：<目标能力>
适用范围与执行频率：<每次发布；或明确的模式/平台/账户条件>
前置条件：<候选版本、环境、权限、夹具和所选模型>
提示词与步骤：<可复制且不依赖私人路径或旧会话 ID>
通过条件：<可观察、可核验的行为及禁止的替代路径>
必要证据：<工具调用、生命周期、文件/外部结果和边界检查>
失败与未执行判定：<如何区分，哪些结果不能视为通过>
收尾要求：<只处理本次归属明确的测试资源，保留证据>
```

用例描述保持长期可执行；具体版本是否通过属于版本结果，不写成永久通过结论。
