# 按变更影响验收协议

[English](acceptance-protocol.md) | [简体中文](acceptance-protocol.zh-CN.md) · [开发手册](development.zh-CN.md) · [发布手册](release.zh-CN.md)

本协议规定开发变更和发布的验收范围、证据复用及完成条件。[能力目录](acceptance-tests.zh-CN.md)定义可观察要求，[证据手册](acceptance-evidence.zh-CN.md)定义存储及检查器支持情况。旧清单如被理解为每次修改后重跑全部能力，应按本协议选择执行范围；必需行为和证据层级要求保持有效。

## 验收单位与责任

一个验收批次对应一项完整行为变更，包含实现、测试及文档，不对应每次文件保存、聊天轮次或回执更新。行为稳定后确定测试快照；后续修改只重新评估受影响检查点。

区分开发验证、业务验收和发布就绪。开发者提供实现与回归证据，测试复核检查覆盖与结果，业务验收评估新增或明显改变的用户工作流。小团队可以兼任。普通变更按协议执行，无需每项测试审批；高风险范围判断和例外由维护者复核。发布以及接受未解决发布风险是独立决定。

## 能力、检查点、流程与证据

| 对象 | 必需内容 |
| --- | --- |
| 能力 | 稳定的CAP/Q编号、预期行为及适用条件。 |
| 检查点 | 前提、可观察预期结果、模式/平台/配置及所需证据层级；仅在结果或复验范围可独立判断时拆分。 |
| 流程 | 可重复的准备、步骤、观察及收尾；一条流程可以覆盖多个检查点和能力。 |
| 执行 | 唯一执行ID、实际源码/运行时或制品、环境、流程/数据版本、各检查点结果及证据引用。 |
| 有效性评审 | 目标候选、原证据、累计差异、影响理由和复核者；解释复用，不改变原执行身份。 |

CAP/Q是覆盖索引，不是独立执行任务。能力满足条件是所有适用必需检查点都有有效证据；缺少一个检查点不会抹去其他结果。夹具、认证DEV和原生包证据保持各自含义，不能替代彼此独有边界。

## 变更影响计划

昂贵执行开始前，记录简短计划：

1. 改变的行为、目的及可观察的成功标准。
2. 证据基线，以及各相关基线到目标的累计差异，包含未提交修改；不能只看最后一次提交。
3. 受影响组件、调用方、共享状态、接口、权限、数据、配置、构建/运行时依赖、平台和外部服务。
4. 修复确认、回归检查点、可复用证据及排除理由；同类理由可合并说明。
5. 合并后的流程、预计成本、前提、退出条件及已知阻碍。

风险取决于失败后果、共享行为和不确定性，不取决于修改行数。授权、文件变化、重复执行、队列归属和物理资源清理属于高风险领域。未修改文件也可能经依赖受影响。依赖图和覆盖率辅助分析，但不能证明不存在动态影响。影响不明时扩大到相关子系统；架构广泛变化或基线不可信时可能需要完整回归。

| 变更 | 默认取证范围 |
| --- | --- |
| 说明文档或拼写 | 内容、链接和双语一致性；承诺变化时复核对应标准，参与生成行为/配置时按产品变更处理。 |
| 局部界面 | 相关交互、渲染、语言/窗口尺寸、类型和构建检查。 |
| 局部业务或API | 修复确认、相关单元/契约/集成测试及必要用户流程。 |
| 共享浏览器、队列、取消或工具交接 | 相关回归与历史缺陷用例、受影响适配器契约及必要认证流程。 |
| 授权或持久化/数据格式 | 成功/拒绝、兼容、迁移/恢复及受影响真实流程。 |
| 运行时、关键依赖、打包或安装 | 受影响集成、目标制品/平台及适用的一次性操作系统检查。 |
| 广泛或不明确的影响 | 扩大子系统回归或建立新的完整基线，记录理由。 |

在能证明目标的最低合适层验证。错误分支、竞争和参数边界使用确定性测试，实际浏览器/工具交付使用真实流程，操作系统行为使用原生检查。适当时在集成或候选冻结阶段集中运行一次成本可接受的稳定自动化套件。已有等价有效结果时，不为新增回执或汇报重跑；昂贵认证/人工流程按影响计划执行。

## 共享流程与参数覆盖

先选择必需检查点，扣除已有有效证据，再为缺口选择流程。优先合并前提兼容、观察有用且失败可定位的流程，不追求一个巨大脚本覆盖全部。

| 可复用流程 | 可共享的检查点证据 |
| --- | --- |
| 读取→补丁→命令回读→续轮/结束 | 工具交付、实际文件、明确模型/力度、发送记账、日志及收尾；需要时加入同cell等待。 |
| 单名额父任务与三个子任务 | 委派、实际结果、父任务让出/重新取得名额、容量及清理。 |
| 设置与权限变化 | 保存/默认草稿、热应用、持久化、拒绝及相关布局。 |
| 受控故障→物理清理→后续任务 | 截止时间、取消、不重发、容量恢复及诊断关联。 |
| 压缩与续轮 | 上下文预算、发送/记账、间隔及队列归属。 |
| 原生诊断导出 | 保存/取消、实际归档、脱敏及故障关联。 |
| 制品与部署 | 完整性、平台启动及适用的安装/升级/恢复。 |

仅合并构建、环境和前提兼容的检查，或明确描述其状态转换。每个声称满足的检查点须有对应步骤的观察。同次执行可供多个CAP/Q引用，不能因为观察到部分行为就把整项能力判为通过。

Native Tools、Automatic MCP与Manual MCP具有不同边界。共享实现证据可以复用，发生变化的模式专属行为须单独取证。模型/力度/平台变体依据实现的等价类、边界和已知交互选择；保留用户明确选择及已承诺差异。没有识别出交互时不执行全部笛卡尔组合，也不能从一个模式通过推断未测试模式通过。

## 证据有效性与继承

原执行记录不可变。目标候选可以采用本次执行，或经评审仍有效的其他候选执行，两者明确标注。复用必须同时满足：

- 通过证据完整可核验，没有后续未解决失败推翻相关行为结论。
- 适用标准、证据层级和相关实现/契约前提仍有效。
- 累计变化不影响行为、传递依赖、配置、数据和构建前提，或已有补充证据解决相关影响。
- 环境前提仍适用，包含运行时/浏览器、平台、模式和外部接口。
- 明确引用原执行、目标身份、比较范围、影响理由和复核者，保留此前失败。

整个源码摘要仍用于溯源，但不是所有能力失效的唯一依据。按需记录制品/运行时、流程/数据和环境身份。仅文档导致源码变化，不必使工具执行结果失效；新的实际制品仍须有适用的自身检查。

修复记录器不会否定可独立核验的早期结果。修复漏断言、错误判定或假阳性测试时，须复核所有依赖该判定的结果。缺失或此前未证明的检查点不能通过继承变成通过。

外部网页和连接器可能在仓库未变时变化。新认证批次先做轻量就绪/绑定检查，接口漂移或无法解释的失败使相关检查点需复验。发布前刷新支持的外部关键路径所需证据；本批次已有合格的同候选执行可以提供，不另开重复任务。不以任意时间期限让全部证据失效，也不假定外部证据永久有效。

## 执行与失败处理

1. 稳定变更快照，完成影响计划。
2. 映射有效证据和缺口，合并兼容流程。
3. 先执行相关静态/单元/接口检查，再执行必要系统/认证流程；低层失败先修复，再启动依赖它的长任务。
4. 预检DEV归属、必要绑定/权限、命令入口、选择器及取证方式；同批次共享准备。
5. 同次执行采集各检查点结果，先诊断失败再决定重试。
6. 核对物理清理和隔离边界，更新覆盖，满足退出条件即结束；没有新改动、失败或未解风险时，不扩大或重复。

所有执行遵循[隔离流程](development.zh-CN.md#standard-isolated-test-procedure)。归属不变时可共享批次前后生产边界快照，模式、隧道或进程变化时补充核验。仅在已加载实现/配置需要时重启已确认DEV；单纯源码元数据变化不要求重启正常运行时。保留沙箱、审批、模型/路由、独立认证及一次性操作系统边界。

| 失败类别 | 必需处理 |
| --- | --- |
| 产品缺陷 | 保留失败，修复后确认原失败行为并回归受影响路径；不得重试到偶然通过。 |
| 外部/本机网络中断 | 核实恢复后通常重试受影响流程一次；持续失败记环境阻碍，转做独立工作，不改无关产品或本机设置。 |
| 驱动或取证错误 | 修正并预检驱动，补独立缺口，保留有效观察。 |
| 不明/偶发失败 | 保持未解决并针对性定位，不推定是网络或已经通过。 |
| 工具不可用或负责人操作项目 | 记录具体缺口、责任和前提，既不算产品失败，也不算通过。 |

续测须核实前置状态。独立观察可单独补充；并发、连续会话、取消竞争和事务性质须执行能证明该性质的最小完整流程，不能拼接无关执行宣称一次成功。网络中断不能掩盖永久占用容量等产品不变量违反。

## 完成与发布

变更验收完成条件：目标行为及受影响回归具有有效证据，相关阻断缺陷已解决，适用权限/数据/清理不变量成立，范围和结果可追溯。无关问题另行记录，除非会推翻当前结论。业务UAT关注新增或明显变化的工作流，成熟功能每次修复不要求用户重验整个产品。

包括预览版在内，发布要求：

1. 适用承诺能力具有有效覆盖，由本次执行与经评审继承的证据共同组成；未知项目继续未知。
2. 各相关证据基线以来的累计变化有增量验收，无未解决阻断缺陷。
3. 实际发布制品的完整性、启动及必要关键路径冒烟证据，以及发布手册规定的适用平台/安装/升级检查；旧制品不能证明新制品行为。

首次建立基线、广泛架构/协议或重大运行时/环境变化、影响无法界定、基线可信度丢失时重建完整能力基线。每次小版本不默认重跑昂贵的全部认证能力。候选冻结时可集中进行一次成本可接受的全量自动化。本批次已有合格执行可兼作发布冒烟，不因名称不同重复执行。

报告分别列出**本次实测、既有证据仍有效、需验证、产品失败、环境受阻、负责人操作、不适用及理由**。执行结果与适用性/有效性分开；继承不是新执行，受阻不是豁免，CAP/Q行数不是开发完成百分比。维护者接受发布风险的决定须单独记录，不把例外改写成通过。

## 记录与检查器过渡

使用仓库内简短覆盖表和既有证据存储，无需另建测试管理平台或逐项审批流程。最小映射为：

```text
检查点ID | 能力ID | 标准/必要层级 | 模式/平台
受影响依赖 | 流程/执行ID | 证据及实际结果
目标有效性：本次/继承/需验证/受阻
累计比较及理由 | 复核者/负责人 | 下一步
```

schema-2检查器已实现检查点覆盖、共享执行和累计有效性评审，schema 1继续兼容历史记录。保留原身份和失败，迁移前归档清单，评审目标有效性，不重置全部能力。未知或受影响检查点保持缺口。检查器不鉴定证据真实性，也不替代外部就绪和实际制品检查。详见[证据手册](acceptance-evidence.zh-CN.md#checker-compatibility)。
